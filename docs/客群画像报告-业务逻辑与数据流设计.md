# 客群画像分析报告 — 业务逻辑与数据流设计文档

> 版本：v1.1 | 日期：2026-06-01 | 状态：设计评审修订

## 一、需求概述

基于预定义的标签主题，对筛选出的客群自动生成画像分析报告，支持 PC 端预览并一键导出 Word/PDF。

**核心流程**：选择标签主题 → 系统自动筛选客群 → 生成多维度分析报告 → 导出可编辑文档

---

## 二、业务流程全景

### 2.1 端到端流程

```
┌─────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐

│   配置   │   │   筛选   │   │   分析   │   │   洞察   │   │   生成   │   │ Word/PDF │
│ (管理员) │   │ (系统)   │   │(系统+LLM)│   │(系统+LLM)│   │  (LLM)   │   │  (系统)  │
└─────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 2.2 用户操作流程

```
用户登录 → 选择标签主题 → 预览报告（分章节） → 选择导出格式 → 下载 → 本地编辑定稿
                ↑                                              │
                └──────────── 可返回修改主题重新生成 ────────────┘
```

### 2.3 各阶段职责

| 阶段 | 输入 | 处理 | 输出 | 耗时预估 |
|------|------|------|------|----------|
| ① 标签配置 | 管理员定义 | CRUD 持久化 | 标签主题 + 特征定义 | 人工操作 |
| ② 客群筛选 | 标签主题的 filter_rules | 遍历客户数据匹配规则 | 客群 ID 列表 + 基础统计 | <1s |
| ③ 特征分析 | 客群 ID + 标签特征定义 | 统计聚合 + Top5 排序 + LLM 解读 | 各维度分析数据 + 文案 | 5-10s |
| ④ 相关性洞察 | 客群标签值矩阵 | 交叉统计 + LLM 推理 | 关联规则列表 + 洞察文案 | 3-5s |
| ⑤ 报告生成 | ②③④全部结果 | 组装报告结构 + LLM 生成建议 | 完整报告 JSON | 3-5s |
| ⑥ 导出 | 报告 JSON | 模板渲染 + 图表嵌入 | Word/PDF 文件流 | 2-5s |

**单份报告端到端预估**：15-25 秒（主要耗时在 LLM 调用，共 5-8 次）

#### FilterRule（筛选规则）

```python
class FilterRule(BaseModel):
    field: str       # 客户数据字段路径，如 "aum", "basic_info.occupation"
    operator: str    # ">=", "<=", "==", "in", "not_in", "between", "contains"
    value: Any       # 阈值或枚举值

class FilterGroup(BaseModel):
    """支持 AND/OR 嵌套的筛选规则组，等价于布尔表达式树"""
    logic: str                               # "AND" | "OR"
    rules: list[FilterRule | FilterGroup]    # 叶子节点为 FilterRule，分支为 FilterGroup
```

**规则示例**：

AND 串联（基本场景）：
```json
{ "logic": "AND", "rules": [
    { "field": "aum", "operator": ">=", "value": 1000000 },
    { "field": "lifecycle", "operator": "in", "value": ["成熟期", "衰退期"] }
]}
```
→ AUM ≥ 100万 且 生命周期为成熟期或衰退期。

OR + AND 嵌套（实际业务场景）：
```json
{ "logic": "OR", "rules": [
    { "logic": "AND", "rules": [
        { "field": "basic_info.branch", "operator": "==", "value": "东城支行" },
        { "field": "aum", "operator": ">=", "value": 500000 }
    ]},
    { "logic": "AND", "rules": [
        { "field": "basic_info.branch", "operator": "==", "value": "西城支行" },
        { "field": "aum", "operator": ">=", "value": 300000 }
    ]}
]}
```
→ (东城支行 且 AUM≥50万) 或 (西城支行 且 AUM≥30万)。

### 4.2 Phase ② 客群筛选

**筛选引擎逻辑**：

```python
def segment_customers(theme: TagTheme, all_customers: list) -> list:
    """根据标签主题的 filter_group 筛选客户"""
    return [c for c in all_customers if _match_group(c, theme.filter_group)]

def _match_group(customer: dict, group: FilterGroup) -> bool:
    """递归评估 FilterGroup（支持 AND/OR 嵌套）"""
    results = []
    for rule in group.rules:
        if isinstance(rule, FilterGroup):
            results.append(_match_group(customer, rule))
        else:
            results.append(_match_rule(customer, rule))
    if group.logic == "AND":
        return all(results)
    return any(results)  # "OR"

def _match_rule(customer: dict, rule: FilterRule) -> bool:
    value = _get_nested_field(customer, rule.field)
    if value is None:
        return False  # 字段缺失视为不匹配
    match rule.operator:
        case ">=": return value >= rule.value
        case "<=": return value <= rule.value
        case "==": return value == rule.value
        case "in": return value in rule.value
        case "not_in": return value not in rule.value
        case "between": return rule.value[0] <= value <= rule.value[1]
        case "contains": return rule.value in value
    return False
```

### 4.3 Phase ③ 特征分析

#### 统计计算

```python
def analyze_feature(customers: list, feature: TagFeature, all_customers: list) -> FeatureResult:
    values = [_get_nested_field(c, feature.source_field) for c in customers]
    all_values = [_get_nested_field(c, feature.source_field) for c in all_customers]

    match feature.aggregation:
        case "avg":
            result_value = mean(values)
            chart_data = {"value": result_value}
        case "distribution":
            chart_data = _build_histogram(values, feature.chart_config.get("bins", 5))
        case "enum_count":
            chart_data = _count_enums(values)
        case "count":
            result_value = len([v for v in values if v]) / len(values)

    # 显著性评分
    significance = _calc_significance(values, all_values, feature.data_type)

    return FeatureResult(
        feature_id=feature.id,
        feature_name=feature.name,
        chart_type=feature.chart_type,
        chart_data=chart_data,
        significance_score=significance,
        raw_stats={"mean": mean(values), "std": stdev(values), "count": len(values)},
    )
```

#### 显著性评分算法

**设计决策**：采用 **Z-score 绝对值** 作为主要指标，辅以 **覆盖率差异** 作为补充。

**理由**：
- Z-score 直接反映"该客群的特征值偏离全行平均水平多少个标准差"，业务含义清晰
- 对于枚举型特征，使用"客群中该类别的占比 vs 全行占比"的差值
- 模拟数据量小（~100客户），不需要复杂的统计检验，Z-score 足够

```python
def _calc_significance(seg_values, all_values, data_type) -> float:
    """计算特征显著性分数（0-1，越高越显著）"""
    if data_type == "number":
        seg_mean = mean(seg_values)
        all_mean = mean(all_values)
        all_std = stdev(all_values) or 1  # 防除零
        z_score = abs(seg_mean - all_mean) / all_std
        return min(z_score / 3.0, 1.0)  # 归一化到 [0, 1]，Z=3 时满分
    elif data_type == "enum":
        seg_dist = _distribution(seg_values)
        all_dist = _distribution(all_values)
        # 最大类别占比差异
        max_diff = max(abs(seg_dist.get(k, 0) - all_dist.get(k, 0))
                       for k in set(seg_dist) | set(all_dist))
        return min(max_diff / 0.5, 1.0)  # 差异 50% 时满分
    return 0.0
```

def select_top5(all_results: list[FeatureResult]) -> list[FeatureResult]:

    candidates = [r for r in all_results if r.is_top5_candidate]

### 4.4 Phase ④ 相关性洞察

#### 交叉统计引擎

**设计决策**：采用 **Lift（提升度）** 作为关联强度指标，阈值为 **lift ≥ 1.3 且 support ≥ 3%**。

**理由**：
- 模拟客群样本小（20-50人），lift > 1.5 + support > 5% 会导致规则过少
- lift ≥ 1.3 表示"A 出现时 B 的概率比随机高 30%"，已有业务价值
- support ≥ 3% 确保规则至少在 1-2 个客户上成立，避免噪声
- 过滤掉"显而易见"的关联（如 asset_level == "高净值" → aum > 100万），只保留非平凡规则

```python
# ── 互斥特征组（同一组内的特征不做关联分析，避免同义反复）──
MUTUALLY_EXCLUSIVE_GROUPS = [
    {"asset_level_ratio", "avg_aum", "aum_distribution"},   # 资产维度内部
    {"churn_probability", "lifecycle_distribution"},          # 流失维度内部
    {"product_count", "product_type_distribution"},           # 产品维度内部
    {"aum_mom_change", "aum_yoy_change", "aum_trend"},       # 变化维度内部
]

def discover_correlations(customers, enum_features, numeric_features):
    """发现客群内标签特征间的非平凡关联（枚举-枚举 + 枚举-数值）"""
    rules = []

    # ── 枚举-枚举关联（Lift）──
    for f1, f2 in combinations(enum_features, 2):
        if _in_same_exclusive_group(f1.id, f2.id):
            continue
        vals1 = [_get_nested_field(c, f1.source_field) for c in customers]
        vals2 = [_get_nested_field(c, f2.source_field) for c in customers]
        for v1 in set(vals1):
            for v2 in set(vals2):
                count_a = sum(1 for v in vals1 if v == v1)
                count_b = sum(1 for v in vals2 if v == v2)
                count_ab = sum(1 for a, b in zip(vals1, vals2) if a == v1 and b == v2)
                n = len(customers)
                support = count_ab / n
                lift = (count_ab / n) / ((count_a / n) * (count_b / n)) if count_a and count_b else 0
                if lift >= 1.3 and support >= 0.03:
                    rules.append(CorrelationRule(
                        type="enum_enum",
                        antecedent=f"{f1.name}={v1}",
                        consequent=f"{f2.name}={v2}",
                        support=support, lift=lift,
                        confidence=count_ab / count_a if count_a else 0,
                    ))

    # ── 枚举-数值关联（均值比）──
    for ef in enum_features:
        for nf in numeric_features:
            if _in_same_exclusive_group(ef.id, nf.id):
                continue
            all_mean = mean([_get_nested_field(c, nf.source_field) for c in customers]) or 1
            for v in set(_get_nested_field(c, ef.source_field) for c in customers):
                seg = [c for c in customers if _get_nested_field(c, ef.source_field) == v]
                if len(seg) < 2:
                    continue
                seg_mean = mean([_get_nested_field(c, nf.source_field) for c in seg])
                ratio = seg_mean / all_mean
                if ratio > 1.5 or ratio < 0.67:
                    direction = "显著高于" if ratio > 1 else "显著低于"
                    rules.append(CorrelationRule(
                        type="enum_numeric",
                        antecedent=f"{ef.name}={v}",
                        consequent=f"{nf.name}",
                        ratio=round(ratio, 2),
                        direction=direction,
                        support=len(seg) / len(customers),
                        insight=f"{v}客群的{nf.name}{direction}全行平均（{ratio:.1f}倍）",
                    ))

    rules.sort(key=lambda r: getattr(r, 'lift', getattr(r, 'ratio', 0)), reverse=True)
    return rules[:5]
```

### 4.6 Phase ⑥ 导出

#### 设计决策：前端 canvas 转图片 + 后端模板组装

#### 数据脱敏（#4 银行合规要求）

```python
class ExportConfig(BaseModel):
    desensitize: bool = True           # 默认开启脱敏
    mask_rules: dict = {
        "name": "partial",             # 张三 → 张*
        "phone": "partial",            # 13812345678 → 138****5678
        "id_card": "full",             # 完全遮盖
        "address": "partial",          # 保留省市，隐藏详细地址
    }

def _desensitize(value: str, rule: str) -> str:
    if rule == "full": return "***"
    if rule == "partial":
        if len(value) <= 2: return value[0] + "*"
        return value[0] + "*" * (len(value) - 2) + value[-1]
    return value
```

#### Payload 方案（#10 避免 base64 超限）

采用 **前端先上传图片、后端组装** 的两步方案，避免 POST body 过大：

```
Step 1: 前端上传图表图片
  POST /api/report/{id}/upload-images
  Content-Type: multipart/form-data
  → 后端存临时目录，返回图片路径映射

Step 2: 前端触发导出
  POST /api/report/{id}/export/word  (或 /pdf)
  body: {}  (无 payload，图片已在服务端)
  → 后端从临时目录读取图片，组装文档
  → 返回文件流 + 自动清理临时图片
```

**Word 导出流程**：
```
后端 python-docx:
  1. 读取 docx 模板（预定义的报告样式骨架）
  2. 填充文字内容（摘要、统计、LLM 文案）
  3. 从临时目录读取图表图片并插入
  4. 对客户姓名/手机号等做脱敏处理
  5. 设置页眉页脚（报告名称 + 页码 + 生成日期）
  6. 返回文件流
```

**PDF 导出流程**：
```
后端:
  1. 用 Jinja2 渲染 HTML 报告模板（图表直接引用临时图片路径）
  2. 对客户信息做脱敏处理
  3. Playwright 打开 HTML → 生成 PDF
  4. 返回文件流 + 自动清理临时图片
```

## 七、技术选型决策

### 7.1 显著性评分：Z-score 绝对值

**选型理由**：
- 业务含义直观：Z=1 表示偏离均值 1 个标准差，Z=2 表示显著偏离
- 计算简单，适合模拟数据量（100 客户）
- 归一化到 [0,1] 后可直接用于排序
- 对于枚举型特征，用"占比差值"替代，语义一致

**备选方案（已排除）**：
- 卡方检验：样本量太小，p 值不可靠
- 信息增益：需要决策树结构，过重
- 变异系数（CV）：只反映离散度，不反映"与全行的差异"

### 7.2 关联规则阈值：lift ≥ 1.3, support ≥ 3%

**选型理由**：
- 模拟客群 20-50 人，3% support = 至少 1 人，是最低有效阈值
- lift ≥ 1.3 过滤掉弱关联，保留有业务价值的规则
- 配合 trivial 过滤器（排除定义性关联），确保输出的规则有"意外发现"价值

**备选方案（已排除）**：
- lift > 1.5 + support > 5%：阈值过严，小客群可能 0 条规则
- 皮尔逊相关系数：只适用于连续变量，不适用枚举交叉

### 7.3 报告模板：单模板 + 可配置 sections

**选型理由**：
- 需求明确是单主题报告，不需要多套模板切换
- 通过 TagGroup 配置控制报告的第 3 章有哪些分析维度，灵活性足够
- 模板用 Python 类 + Jinja2 模板，Word 用 python-docx，PDF 用 HTML+Playwright
- 后续扩展多模板时，只需新增模板类，不影响数据层

### 7.4 图表嵌入：前端 canvas 转 base64

**选型理由**：
- ECharts 已在前端渲染，样式完全一致
- canvas.toDataURL() 零额外开发成本
- base64 直接嵌入文档，无需图片文件 IO
- 用户预览和导出看到的图表完全一致

**备选方案（已排除）**：
- 后端 matplotlib 重绘：需要维护两套图表代码，样式难对齐
- 后端 ECharts (Node.js)：需要额外的 Node 服务，架构变重
- 前端 puppeteer 截图：需要 headless 浏览器，不如 Playwright 成熟
